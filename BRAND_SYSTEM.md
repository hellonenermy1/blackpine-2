# Blackpine Brand & Editorial System

This file is the working standard for the Blackpine corporate website. It exists to keep future pages, copy, visuals, and product references coherent as the site grows.

## Position

Blackpine Cybersecurity is a Canadian security engineering company. The website should communicate control, technical depth, discretion, and resilience.

The site should feel closer to a security engineering institution than a generic cybersecurity landing page. Competence is demonstrated through scope, evidence, technical material, engineering decisions, and clear boundaries.

## Audience order

1. Security professionals and internal security teams
2. Enterprise and internal IT teams
3. Technical and operational decision-makers
4. Smaller organizations that need the same ideas explained without jargon

Technical readers should be able to go deeper without making the top-level experience inaccessible.

## Voice

Use short, concrete language. Prefer system nouns and observable actions over marketing adjectives.

Good:
- privileged identity
- administrative access
- evidence
- recovery path
- system boundary
- containment
- ownership
- verification
- consequence
- remediation sequence

Avoid:
- premium
- world-class
- cutting-edge
- next-generation
- military-grade
- unbreakable
- comprehensive solutions
- peace of mind
- best-in-class
- AI-powered unless a specific feature actually is

Do not repeatedly explain what Blackpine is not. State the positive operating standard first; use limitations only where they change a decision or define a boundary.

## Editorial rules

A page should answer a real question. It should not exist solely to fill a navigation slot, target a keyword, or make the company appear larger.

Headings should carry meaning on their own. Avoid repeated landing-page grammar such as eyebrow → slogan → three cards → CTA.

Use evidence before assertion. If a claim depends on a certification, client relationship, audit, office, partnership, response commitment, team scale, or external recognition, verify that it is current and publishable before it appears.

Research should be specific enough to help a reader act. Articles should link primary or authoritative sources where practical and distinguish general guidance from incident-specific advice.

## Visual character

Dark mode is the flagship experience. It should feel like graphite, cold metal, mineral surfaces, and northern forest at night — not neon hacker imagery.

Light mode is a first-class design using technical paper, mineral grey, muted evergreen, and dark ink. It must not feel like an inverted dark theme.

Use the existing Blackpine green as a controlled signal colour, not as decoration. Most of the interface should be neutral.

Structure should come from typography, rules, whitespace, rhythm, diagrams, tables, and real imagery. Major sections should be able to exist with no rounded container around them.

## Typography

The primary stack remains local/system-first. Do not introduce a remote font dependency only for fashion.

Display type should feel controlled rather than loud: large scale, tight tracking, moderate weight. Monospace is reserved for labels, metadata, identifiers, technical notation, and diagrams — not every heading.

## Motion

Motion must explain state, focus, hierarchy, orientation, or relationship.

Appropriate:
- navigation state
- filter state
- theme state
- diagram activity that communicates a system relationship
- subtle control feedback

Avoid:
- generic reveal-on-scroll for core content
- cursor-following effects
- particles
- scanlines
- random parallax
- bouncing icons
- ambient motion with no informational purpose

Respect `prefers-reduced-motion`.

## Photography

Priority order:
1. Real Blackpine material: systems, hardware, workspaces, diagrams, project interfaces, team/process material when available
2. Purpose-selected licensed photography with a clear informational or environmental role
3. Stock photography used sparingly
4. Generated cyber imagery should generally be avoided

The Blackpine environment may include infrastructure, electronics, industrial architecture, Canadian/northern landscape, and close technical detail. Forest imagery is a brand atmosphere, not a substitute for technical content.

Never use hooded hackers, Matrix code, glowing padlocks, anonymous blue server-room people, generic SOC dashboards, or random neon network globes.

## Blackpine topology language

The topology motif combines branching/root structure with networks, control paths, and system dependencies. It should remain abstract and technical. It is not a pine-tree logo repeated as decoration.

Use it for:
- system maps
- architecture diagrams
- section transitions
- dependency views
- security-model diagrams
- selected loading/progress states

## Page hierarchy

Homepage: position → capabilities → method → Labs → research → trust → contact.

Capabilities: explain when to involve Blackpine, review surface, method, deliverables, a concrete illustrative finding, and the engagement boundary.

Research: selected material first, then the broader library. Publishing volume is not a goal.

Trust: document controls, boundaries, data handling, disclosure, and website design without borrowed trust marks.

Labs: only real engineering projects with enough material to document.

Company: explain why Blackpine exists, how it works, and the standard behind public claims.

## Quality test

Before publishing a section, ask:
- Does this say something specific to Blackpine or the security problem?
- Could the same section be pasted onto fifty SaaS sites unchanged?
- Is there evidence or a real operating principle behind the claim?
- Is the visual treatment helping hierarchy or merely adding decoration?
- Can a technical reader inspect the next level of detail?
- Can a non-specialist still understand the decision being discussed?

If the section fails those tests, rewrite or remove it.
